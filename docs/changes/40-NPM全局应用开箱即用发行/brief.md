# 40：NPM 全局应用开箱即用发行

## 用户问题

ozw 已经声明 NPM 包名、版本、主入口、`ozw` 命令入口和预发布构建，但当前用户仍需克隆仓库、安装 pnpm 依赖并在源码目录运行。发布清单仍携带源码和通用脚本，`start` 仍会现场编译，`postinstall` 仍依赖 `tsx`；CLI 读取安装目录中的 `.env`，现有发布脚本只创建提交与标签，没有把经过验收的包发布到 NPM 注册表。

目标用户本来就使用通过 NPM 安装的 Claude Code、Codex 或 Pi，因此 NPM 全局安装应成为 ozw 的主要发行形态。

## 交付目标

- 用户执行 `npm install -g ozw` 后，只需运行 `ozw` 即可启动预编译的 WebUI 和后端。
- 首次运行创建 `~/.ozw/.env`、数据目录和恰好 32 个字符的 `OZW_ACCESS_TOKEN`，并明确展示首次登录方式。
- JWT 签名密钥继续由运行时自动生成并私密保存，不写进用户配置，不要求用户管理。
- 发布包只包含编译后的前后端、运行时静态资源、数据库初始化资源、命令入口和必要文档。
- 在 1 个虚拟中央处理器、512 MiB 内存和可控慢磁盘剖面下，启动、登录页、认证首页和项目列表仍通过分段延迟与事件循环预算。
- 启动和首页请求不等待 Provider 历史遍历、外部命令探测或其他可延后工作；慢路径在后台增量完成。
- ozw 只检测 Claude Code、Codex、Pi 的可用性与认证状态，不负责安装、启动、停止、升级或修改其配置。
- 默认以前台进程运行；系统服务是后续可选能力，必须复用同一运行入口和用户数据目录。
- NPM 发布流水线在干净环境验证安装、启动、升级和卸载，并覆盖 `better-sqlite3` 支持的平台与架构。

## 非目标

- 不在本提案中制作 Electron、macOS、Windows 或 Linux 图形安装包。
- 不把 Node.js、NPM、Claude Code、Codex 或 Pi 打包进 ozw。
- 不让 ozw 管理外部编程代理或 Codex Server 守护进程。
- 不承诺首期提供容器镜像、自动更新器、多用户账号或远程托管服务。
- 不在安装生命周期执行 TypeScript 编译、前端构建或下载浏览器。
- 不承诺任意 NAS 或云服务器都有相同的绝对耗时；发布门禁只对可复现的单核、固定文件规模和注入延迟场景负责。
- 不将 SQLite 数据库位于 NFS、SMB/CIFS、WebDAV 等网络文件系统的部署纳入性能或一致性保证。

## 用户路径

```text
npm install -g ozw
        ↓
       ozw
        ↓
首次创建 ~/.ozw/.env、数据库与内部密钥
        ↓
显示本地地址和 32 位访问令牌
        ↓
浏览器登录并检测已安装的编程代理
```

## 创建阶段基线

| 已具备 | 尚未形成可发行闭环 |
| --- | --- |
| `name`、`version`、`main`、`bin`、`files` | `files` 仍包含 `backend/`、`shared/`、通用 `scripts/` |
| `prepublishOnly` 会构建前后端 | `start` 仍依赖 pnpm 并现场构建 |
| CLI 已能启动和显示状态 | CLI 的 `.env` 与部分状态语义仍以安装包根目录为中心 |
| 数据库默认路径已指向 `~/.ozw/ozw.db` | 首次运行尚未自动创建用户 `.env` 和访问令牌 |
| JWT 密钥已经自动生成 | 仍需验证全局只读安装目录下的权限与持久性 |
| `release.sh` 会更新版本、提交和打标签 | 没有 NPM 注册表发布、产物审计和跨平台安装门禁 |

## 验收入口

- 以 `npm pack` 生成的真实压缩包为唯一候选产物，不从源码目录冒充全局安装。
- 在隔离的用户主目录、NPM 全局前缀和缓存中安装，环境只提供受支持的 Node.js 与 NPM。
- 在统一的低端资源剖面中记录进程到健康、登录页、认证首页、`/api/projects` 首字节和事件循环停顿的冷、热分布。
- 至少覆盖 Linux、macOS、Windows 的受支持架构矩阵，并对 `better-sqlite3` 执行真实打开、迁移和读写。
- 完成后把长期发行约束合并到 `docs/specs/npm-global-distribution.md`，活动提案归档。
