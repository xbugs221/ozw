# 提案：把 ozw 发布为开箱即用的 NPM 全局应用

## 为什么要改

ozw 的目标用户已经拥有 Node.js 与 NPM，因为其服务对象 Claude Code、Codex 和 Pi 本身就通过 NPM 生态安装。继续要求用户克隆源码、安装 pnpm、复制配置并在每次启动时构建，既增加使用门槛，也把开发依赖、源码目录权限和构建工具变成生产运行条件。

仓库已经具备 NPM 包的基本元数据与编译入口，本提案不是从零建立打包系统，而是补齐从“可声明的包”到“可安装、可运行、可升级、可验证的成品”的缺口。

## 做什么

1. 将前端和后端在发布前预编译，`ozw` 命令只运行成品，不调用 pnpm、tsx、tsc 或 Vite。
2. 收紧 NPM 发布清单，只携带生产运行所需资产，并从实际压缩包反向验证完整性。
3. 建立统一用户目录 `~/.ozw`：首次运行安全创建 `.env`、数据库、内部 JWT 密钥和必要状态文件。
4. 在缺少 `OZW_ACCESS_TOKEN` 时自动生成恰好 32 个字符的随机令牌，首次清晰展示；已有配置绝不静默覆盖。
5. 让前台启动、状态诊断和后续可选系统服务共享同一配置解析、数据目录和服务入口。
6. 保留外部编程代理的诊断能力，但明确 ozw 只检测、不管理 Claude Code、Codex、Pi 和独立 Codex Server。
7. 建立 `better-sqlite3` 跨平台安装矩阵、干净环境验收、NPM 发布流水线和发布后冒烟检查。
8. 约定标准 NPM 升级与卸载行为，卸载程序不删除用户数据，数据清理必须是显式命令或手工动作。

## 预期结果

| 用户动作 | 系统行为 | 用户不再需要 |
| --- | --- | --- |
| `npm install -g ozw` | 安装已经构建并验收的生产包 | Git、pnpm、TypeScript、Vite |
| 首次执行 `ozw` | 初始化 `~/.ozw` 并启动服务 | 手工复制 `.env`、生成 JWT 密钥 |
| 浏览器首次登录 | 输入自动生成的 32 位访问令牌 | 注册账号、选择管理员 |
| `ozw status` | 显示真实配置、数据路径和依赖诊断 | 进入全局包安装目录排查 |
| `npm update -g ozw` | 替换程序，保留 `~/.ozw` 数据 | 重新克隆和构建 |
| `npm uninstall -g ozw` | 移除程序，默认保留用户数据 | 担心卸载误删项目和会话 |

## 成功标准

- 干净机器只安装受支持的 Node.js 与 NPM，即可通过公开注册表安装并启动 ozw。
- 安装和启动过程中不读取源码树，不要求 pnpm，不执行开发构建。
- NPM 压缩包内容可审计，缺少任何生产资产都会在发布前失败，多带源码、测试或开发工具也会失败。
- 首次初始化可重复执行且不会覆盖用户已有令牌、数据库或内部密钥。
- 每个声明支持的平台都通过真实全局安装和 SQLite 读写；没有通过的平台不得出现在支持列表。
