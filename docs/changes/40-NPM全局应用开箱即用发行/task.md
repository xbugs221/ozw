# 任务：NPM 全局应用开箱即用发行

## 1. 固化当前基线和发行合同

- [ ] 记录现有 `name`、`version`、`main`、`bin`、`files`、`prepublishOnly`，避免重复建设已经存在的包元数据。
- [ ] 为真实 `npm pack` 增加内容、入口、体积和必要资产合同。
- [ ] 在隔离用户目录与全局前缀中复现当前失败：启动依赖 pnpm/tsx、配置指向安装目录、注册表未发布。
- [ ] 明确首个支持的 Node.js、操作系统与架构矩阵。

## 2. 建立预编译成品边界

- [ ] 调整发布构建，使后端、前端和数据库资源一次构建后可直接运行。
- [ ] 让 `ozw` 命令只执行编译产物，不调用 pnpm、tsx、tsc 或 Vite。
- [ ] 移除或替换依赖 `tsx` 的 `postinstall`，证明安装生命周期不构建产品。
- [ ] 把 `files` 收紧为生产允许列表，移除 `backend/`、`shared/` 和整个通用 `scripts/` 源码目录。
- [ ] 从解包后的真实压缩包启动并验证 WebUI、API、WebSocket 与数据库资源。

## 3. 统一首次初始化和用户目录

- [ ] 抽出 CLI、服务端、状态诊断和系统服务共用的用户路径与配置解析。
- [ ] 把默认 `.env` 迁移到 `~/.ozw/.env`，保留显式环境变量最高优先级。
- [ ] 首次运行自动生成恰好 32 个字符的 `OZW_ACCESS_TOKEN`，安全写入并仅在新生成时展示。
- [ ] 保持 JWT 签名密钥由运行时自动生成，不写进 `.env` 或帮助文档。
- [ ] 验证重复启动、并发启动、只读全局安装目录和异常中断不会覆盖已有数据。
- [ ] 让 `ozw status` 报告实际生效的配置、数据库和安装路径。

## 4. 收敛依赖诊断边界

- [ ] 统一 Claude Code、Codex、Pi 和独立 Codex Server 的检测结果与错误提示。
- [ ] 增加合同，证明检测不会安装、启动、停止、升级或修改外部程序配置。
- [ ] 验证可选代理缺失时 ozw 主服务仍能启动，影响只落在对应功能。

## 5. 建立安装、升级和卸载验收

- [ ] 用候选压缩包在隔离 NPM 前缀执行真实全局安装与首次启动。
- [ ] 从旧版用户目录升级到候选版，验证令牌、JWT 密钥、数据库和业务数据保持。
- [ ] 卸载全局包，验证 `~/.ozw` 默认保留且不存在隐式数据清理脚本。
- [ ] 增加旧数据库迁移失败的保护与恢复验证。
- [ ] 更新中英文 README 和快速开始，把 NPM 全局安装作为主路径，源码安装降为开发路径。

## 6. 建立低端单核与慢磁盘性能门禁

- [ ] 建立固定 Linux 性能剖面：1 个虚拟中央处理器配额、512 MiB 内存、本地状态与 Provider 夹具磁盘 20 ms I/O 延迟和 10 MiB/s 吞吐上限。
- [ ] 生成 100 个项目摘要、5000 条索引会话和 10000 个带固定小正文的 Provider 历史文件夹具，外部代理探测固定延迟 2 秒或不可用。
- [ ] 分别记录首次初始化到 `/health`、已初始化进程到 `/health`、登录页 HTML 首字节与认证状态、认证首页可用和 `/api/projects` 首字节。
- [ ] 对新进程冷路径和同进程热路径各采样至少 20 次，保存中位数、95 分位、最大值、文件系统操作数和读取字节数。
- [ ] 在 Provider 索引和 4 个首页请求并行时采样事件循环停顿，执行 95 分位 100 ms、单次 250 ms 的门禁。
- [ ] 证明进程健康前不遍历 Provider 历史或等待外部探测，`/api/projects` 不遍历 Provider 目录或读取 transcript 正文。
- [ ] 把 transcript 正文体积扩大 10 倍，验证项目列表文件操作数不变且 95 分位增幅不超过 10%。
- [ ] 仅在证据证明 CPU 工作持续阻塞事件循环时引入 Worker 或独立进程，不把多线程作为默认改造目标。
- [ ] 在中英文部署文档说明 NAS 可运行 ozw，但 `DATABASE_PATH` 应指向 NAS 本机磁盘卷；网络文件系统上的 SQLite 不纳入性能或一致性保证。

## 7. 验证原生数据库支持矩阵

- [ ] 确认生产实际需要的 `better-sqlite3`、`sqlite3` 与封装依赖，移除无调用方的重复原生依赖。
- [ ] 在 Linux x64/arm64、macOS x64/arm64、Windows x64 候选矩阵执行安装、加载、迁移和读写。
- [ ] 记录使用上游预编译二进制或回退本机编译的情况，不用预装工具链掩盖失败。
- [ ] 只在文档中声明真实通过的 Node.js、平台和架构组合。

## 8. 建立受保护的 NPM 发布流水线

- [ ] 明确 `release.sh` 只负责版本准备和标签，或把其职责迁入自动化流水线。
- [ ] 增加质量门、单次构建、`npm pack` 审计、跨平台安装矩阵和人工批准条件。
- [ ] 使用受保护的 NPM 发布身份，检查包名所有权、版本、标签和压缩包摘要。
- [ ] 发布矩阵已经验收的同一压缩包，不在发布步骤重新构建。
- [ ] 发布后从公开注册表重新安装，验证版本、首次初始化、健康检查和 WebUI。
- [ ] 为失败发布准备弃用、回滚和修复版本流程。

## 9. 后置实现可选系统服务

- [ ] 前台发行稳定后，再设计 Linux、macOS、Windows 的 ozw 自身服务适配。
- [ ] 服务复用相同 CLI、用户目录、配置和停止信号处理。
- [ ] 服务安装、状态和卸载操作保持幂等，不管理任何外部编程代理。
- [ ] 验证 NPM 升级或卸载不会留下指向失效程序路径的服务定义。

## 10. 完整验证与归档

- [ ] 运行 `acceptance.json` 中全部必要测试并保存产物清单、平台矩阵和安装日志。
- [ ] 执行完整代码质量门与浏览器健康检查。
- [ ] 把稳定需求合并到 `docs/specs/npm-global-distribution.md` 并更新规格索引。
- [ ] 归档本提案，只在活动目录保留未完成变更。
